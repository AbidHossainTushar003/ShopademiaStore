Distributed commerce consistency model (P0)External payment/courier systems are outside MySQL ACID. Therefore:State machines (§6) are the only way status changes.Idempotency keys on every mutating checkout/payment/refund/shipment API (Idempotency-Key header, stored with request hash and response).Inventory reservations with expires_at; a job releases expired reservations. Reserve at order creation; consume at confirmation/shipment per ledger rules.Webhooks + reconciliation: provider events are stored first (payment_events, unique (provider, provider_event_id)), then processed; a scheduled reconciliation job compares provider truth with local state and raises alerts on mismatch.Compensating actions: if payment verified but stock cannot be committed → order enters ON_HOLD_EXCEPTION, advance refund workflow starts, admin alerted. Never silently drop a paid advance.Transactional outbox: business transaction writes an outbox_events row; a worker publishes notifications/jobs. Events carry event_id, event_type, event_version, occurred_at, producer, payload.Timeouts: HTTP, DB query, outbound provider, upload — all explicit (values in config, defaults in §9.4).Retries: exponential backoff + jitter, bounded attempts, dead-letter queue; no unbounded synchronous retry; circuit breaker on repeated provider failure.Lock ordering (deadlock avoidance): always customers → carts → inventory_items (ordered by variant_id ASC) → orders → payments. Deadlock → bounded retry (max 3) with idempotency.Isolation: default REPEATABLE READ (InnoDB); inventory reservation uses SELECT … FOR UPDATE on ordered rows; exceptions documented in an ADR.6. Pricing, tax, coupons, money7.1 Price resolution (deterministic)variant.price (global default) → store_variant_prices.price_override if present and active → sale price if within window → coupon/discount → tax → shipping. Calculated server-side only and snapshotted into the order.7.2 Coupons/discounts (full engine)Types: percent, fixed amount, minimum order, product-specific, category-specific, date-limited campaign, usage limit, per-customer limit, store scope, stackability rule. Redemptions recorded in coupon_redemptions with unique constraints preventing double use; validation endpoint rate-limited; coupon abuse feeds the risk layer.7.3 Tax engineData-driven: tax_classes, tax_rates(store_id, class, rate_bp, effective_from, effective_to), tax_inclusive flag per store, jurisdiction fields, exemption support, rounding mode. No hard-coded rate. If no rate configured → tax = 0 and the response/invoice flags tax_not_configured. Tax amount, rate and class are snapshotted per order line.7.4 Rounding and moneyInteger arithmetic only. Percentages in basis points. Rounding rule: half-up at line level, then sum; discount allocated across lines proportionally with the remainder assigned deterministically to the last line. One shared money library; no ad-hoc math.7.5 Order snapshotorder_items snapshot: product name, variant name, SKU, unit price, sale price, discount, tax rate/amount, currency, quantity. Orders snapshot shipping address, delivery fee, advance required, and store settings relevant at purchase. orders.currency_code is immutable (BDT).7.6 IdentifiersHuman-readable order numbers STORECODE-YYYYMMDD-NNNNNN (unique), internal BIGINT UNSIGNED IDs, plus public opaque IDs where exposure matters. SKU globally unique per variant. Slug unique per store among non-deleted products (UNIQUE(store_id, slug) on product_stores). Soft delete never frees a SKU or slug.7.7 VariantsAttributes (size, color, material, storage, weight, custom). Each variant has its own SKU, price, inventory, barcode (optional: GTIN/EAN/UPC/internal code), weight, dimensions.8. Security model (P0)8.1 Authentication — customersAccount ID = BD mobile number (normalized E.164, +8801XXXXXXXXX), unique per store. Email is required (OTP delivery), unique per store.Password: bcrypt cost 12 (or Argon2id via ADR), min length 10, common-password check.Email OTP challenges: 6–8 digits, hashed at rest, TTL 10 min, single use, max attempts, per-account/per-IP/per-store rate limits, resend cooldown. Used for: signup verification, password recovery, email/phone change, suspicious login, high-risk account actions, guest-checkout verification (per-store setting).Account-enumeration protection: identical responses/timing for existing and unknown accounts.Guest checkout: guest orders stored with contact snapshot; claimable later by verified email.8.2 Authentication — adminsEmail + password + MFA (TOTP) mandatory for super_admin, policy-controlled for others (recommended: required for anyone with financial or admin-management permissions).Recovery codes (hashed). MFA reset only by another super admin with approval, or break-glass offline procedure (no public recovery endpoint; audited; time-limited elevation).Admin sessions listable/revocable; admin forced logout.8.3 Tokens and sessionsAccess JWT 15 min, audience-separated (aud=admin|customer), signed with distinct secrets/keys (kid-versioned for rotation). Carries sub, store_id, security_version.security_version on the account/session is bumped on role change, disable, password change, MFA reset, forced logout, incident → older tokens are rejected immediately for sensitive operations and within a bounded period for others. Sensitive admin operations perform a live authorization check against the DB, not just the token.Refresh tokens: random, hashed, rotated on use, token-family reuse detection (reuse → revoke family and flag), idle and absolute lifetimes, logout, logout-all, password-change revoke-all.Browser refresh token: HttpOnly; Secure; SameSite cookie. Android/iOS: bearer in encrypted storage.8.4 CSRF / CORS / browser securityCookie-authenticated state-changing requests require a CSRF token via custom header plus Origin/Sec-Fetch-Site validation; GET/HEAD never mutate state. Bearer-token clients are exempt by design.CORS: per-store registered origins only; never * with credentials; Origin validated server-side.Headers: CSP, HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, frame-ancestors. Payment-related pages use script integrity controls.Storefront renders API text as text, never raw HTML.8.5 Store identificationX-Store-Key is a Public Store Key: it identifies the store; possession MUST NEVER authorize privileged operations. Stored hashed; revocable/rotatable; origin-bound; rate-limited. Admin operations never depend on it.8.6 Authorization and approvalsModel: role → permissions → action → resource → store scope. Admin role assignments carry store_id (or all stores). Deny by default; function-level checks on every route; BOLA checks (ownership/store) on every object access; property-level allowlisted input DTOs (no ...req.body).Minimum permissions: products.read|create|update|delete, orders.read|update|cancel, refunds.create|approve, inventory.read|adjust, stores.manage, payment_config.manage, admin_users.manage, coupons.manage, reviews.moderate, couriers.manage, risk.manage, audit.read, privacy.manage.Base roles: super_admin, admin, catalog_manager, order_manager map to permission sets; custom roles allowed.High-risk actions need confirmation/approval: refunds, large inventory adjustments, payment configuration changes, store credential regeneration, admin role changes, disabling security controls. Flow: request → permission check → fresh re-authentication (MFA step-up) → approval (maker-checker above a configurable threshold; V1 minimum = step-up confirmation) → audit → execute. The last super_admin cannot be disabled or demoted.8.7 Payment security boundaryNo raw card data; hosted/tokenized flows only; PCI scope assessed against provider and implementation — the system MUST NOT claim &quot;PCI compliant&quot;.Webhooks: preserve the raw request body until the signature is verified; constant-time compare; reject missing/invalid signature, replay, stale timestamp, malformed payload; store provider_event_id, type, received_at, event_created_at, signature status, processing status, failure_count; UNIQUE(provider, provider_event_id); duplicates produce no second side effect.Never trust provider-reported amount/currency/status without matching local expectations.8.8 Commerce abuse / risk layerrisk_events, risk_scores, blocklist(phone|address|email|device|ip). Signals: velocity (orders per phone/address/IP/device), repeated cancellations, delivery failures, refused COD, failed advance verification, coupon abuse, multi-account patterns, reservation hoarding. Actions: allow, require advance, require OTP, hold for admin review, block. Thresholds per store. Extension point for ML later; no black-box auto-ban without an admin-visible reason.8.9 Other API securityRate limits by class (login, OTP, register, checkout, advance submission, coupon, search, listing, admin, webhook, upload) at IP/account/store/endpoint levels with 429 + Retry-After. SSRF rules for any server-side URL fetch (allowlist, block private/loopback/link-local, redirect/size/time limits). Upload rules: magic-byte check, extension + content-type check, decode validation, pixel/size/time limits, metadata stripping, random object names, storage outside the executable root, malware scanning where available. No debug/test/env-dump endpoints in production. API inventory enforced (every route in OpenAPI). Security tests cover OWASP API Top 10 categories (BOLA, BFLA, mass assignment, store isolation, token confusion, webhook replay, price manipulation, inventory race, ID enumeration).8.10 AuditAppend-only audit_logs (actor, store scope, action, entity, before/after hashes, IP, user agent, request_id, outcome). The API's DB account has INSERT/SELECT only on it. High-value events are additionally hash-chained and optionally shipped to an external sink.8.11 Data classificationPUBLIC, INTERNAL, CONFIDENTIAL (addresses, phone, email, order contents), HIGHLY_SENSITIVE (MFA secrets, payment references), SECRET (keys, hashes). Field-level encryption for HIGHLY_SENSITIVE fields; blind indexes for searchable encrypted fields; log redaction for authorization headers, cookies, tokens, passwords, OTPs, API keys, signatures, PII.9.
